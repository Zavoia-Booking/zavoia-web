## 1. Canonicalization: rel="canonical" requirements, redirect vs canonical, URL letter case and tracking parameters

### Takeaway
A canonical declaration is "a hint, not a rule". Redirects and `rel="canonical"` are both "strong" signals, and a sitemap is a "weak" one. The signals stack. `rel="canonical"` counts only inside a valid `<head>`: the first invalid element ends Google's head parsing. Use absolute URLs, one canonical per page, and the same URL across methods. Since 17 December 2025 Google also requires the same canonical in the raw HTML and in the JavaScript-rendered DOM. For duplicates you want to retire (for example numeric-ID aliases or case variants), Google's documented tool is a permanent server-side redirect (301/308). Use `rel="canonical"` when the duplicate URLs must keep working (for example tracking parameters). Google treats URL paths as case-sensitive.

- "Keep in mind that these methods can stack and thus become more effective when combined. - "You can indicate your preference to Google using these techniques, but Google may choose a different page as canonical than you do, for various reasons. That is, indicating a canonical preference is a hint, not a rule." — [What is canonicalization](https://developers.google.com/search/docs/crawling-indexing/canonicalization) — LU 2026-08-20, retrieved 2026-11-12
- "The canonical page will be crawled most regularly; duplicates are crawled less frequently in order to reduce the crawling load on sites." — [What is canonicalization](https://developers.google.com/search/docs/crawling-indexing/canonicalization) — LU 2026-08-20, retrieved 2026-11-12

**HTTPS preference**
- "Google prefers HTTPS pages over equivalent HTTP pages as canonical, except when there are issues or conflicting signals such as the following: The HTTPS page has an invalid SSL certificate. The HTTPS page contains insecure dependencies (other than images). The HTTPS page redirects users to or through an HTTP page. The HTTPS page has a `rel="canonical"` `link` to the HTTP page." — [consolidate-duplicate-urls](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls) — LU 2026-07-10, retrieved 2026-11-12

### Inferences
- **Numeric-ID alias of a slug URL:** Google's documentation points to a permanent server-side redirect (301 or 308), because the alias is a duplicate being "deprecated". The redirect is the strongest signal and makes the slug the URL shown in results. Keep a self-referencing canonical on the slug, list only the slug in the sitemap and link internally only to the slug. The signals stack. `rel="canonical"` alone is an acceptable fallback if the alias must keep returning 200, but it remains a hint.
- **Letter-case variants:** Google treats `/Foo` and `/foo` as two URLs. If both return 200 with the same content, they are duplicates that Google must cluster. Normalising to one case, by redirect or at minimum by canonical, matches the documented advice.
- **Canonical in `<body>`:** ignored ("only accepted if it appears in the `<head>`"). Any `iframe`/`img` or other invalid element earlier in the `<head>` also hides canonical and hreflang links that come after it. This differs from robots meta, which Google honours in `<body>`.
- **Canonical pointing at a 4xx/5xx, redirecting or noindexed URL:** no page says what happens. Canonical is only a hint, Google indexes only 200 pages, and a declared canonical must be "similar", so such a declaration most likely cannot win. Google would then choose its own canonical. This is an inference, not a documented rule.
- **Raw vs rendered HTML:** Google canonicalizes "before and after rendering". A canonical present in the server HTML that JavaScript later changes sends two different signals. Since December 2025 the documentation explicitly treats this as wrong.

### Gaps
- No current Google page states the exact outcome when `rel="canonical"` points to a non-200, redirected or noindexed URL. Only the indirect statements above exist.
- The documentation says multiple or conflicting canonical tags "may lead to unexpected results". It does not say whether Google ignores all of them or picks one.
- Google gives no stated preference for lowercase over uppercase. It only says to pick one case.

## 2. hreflang: requirements, methods, broken or ineligible targets, and agreement with canonical

### Takeaway
Each language version must list itself and every other version, with fully-qualified URLs and valid ISO 639-1 language codes (optional ISO 3166-1 Alpha-2 region or ISO 15924 script). `x-default` covers unmatched languages. HTML `<link>` in a valid `<head>`, the HTTP `Link:` header and sitemap `xhtml:link` are equivalent, so use one. Google drops unconfirmed (non-reciprocal) pairs one at a time. Per Google's office hours, a `noindex` URL cannot join a cluster. The canonical must be in the same language. Since 2026-09-21 the docs say hreflang values are case-insensitive, and region codes such as `es-419` are explicitly unsupported.

### Cited Findings
**Purpose and what hreflang is not**
- "Use `hreflang` to tell Google about the variations of your content, so that we can understand that these pages are localized variations of the same content. Google doesn't use `hreflang` or the HTML `lang` attribute to detect the language of a page; instead, we use algorithms to determine the language." — [Tell Google about localized versions of your page](https://developers.google.com/search/docs/specialty/international/localized-versions) — LU 2026-09-21, retrieved 2026-11-12
- "Note that even without taking action, Google might still find alternate language versions of your page, but it is usually best for you to explicitly indicate your language- or region-specific pages." — [same page](https://developers.google.com/search/docs/specialty/international/localized-versions) — LU 2026-09-21, retrieved 2026-11-12

**Three equivalent methods**
- "There are three ways to indicate multiple language/locale versions of a page to Google: HTML HTTP Headers Sitemap. The three methods are equivalent from Google's perspective and you can choose the method that's the most convenient for your site. While you can use all three methods at the same time, there's no benefit in Search (in fact, it maybe be much harder to manage three implementations instead of just picking one)." — [localized-versions](https://developers.google.com/search/docs/specialty/international/localized-versions) — LU 2026-09-21, retrieved 2026-11-12

**Guidelines for all methods (reciprocity, self-reference, absolute URLs, x-default)**
- "Each language version must list itself as well as all other language versions." — [localized-versions](https://developers.google.com/search/docs/specialty/international/localized-versions) — LU 2026-09-21, retrieved 2026-11-12
- "Alternate URLs must be fully-qualified, including the transport method (http/https), so: `https://example.com/foo`, not `//example.com/foo` or `/foo`" and "Alternate URLs do not need to be in the same domain." — [same page](https://developers.google.com/search/docs/specialty/international/localized-versions) — LU 2026-09-21, retrieved 2026-11-12
- "If two pages don't both point to each other, the tags will be ignored. This is so that someone on another site can't arbitrarily create a tag naming itself as an alternative version of one of your pages." — [same page](https://developers.google.com/search/docs/specialty/international/localized-versions) — LU 2026-09-21, retrieved 2026-11-12
- "If it becomes difficult to maintain a complete set of bidirectional links for every language, you can omit some languages on some pages; Google will still process the ones that point to each other." — [same page](https://developers.google.com/search/docs/specialty/international/localized-versions) — LU 2026-09-21, retrieved 2026-11-12
- "Consider adding a fallback page for unmatched languages, especially on language/country selectors or auto-redirecting home pages. Use the the `x-default` value: `<link rel="alternate" href="https://example.com/" hreflang="x-default" />`" — [same page](https://developers.google.com/search/docs/specialty/international/localized-versions) — LU 2026-09-21, retrieved 2026-11-12
- "The reserved `x-default` value is used when no other language/region matches the user's browser setting. […] While you can use the `x-default` value for any page, it was designed for language selector pages and so it will work best with those." — [same page](https://developers.google.com/search/docs/specialty/international/localized-versions) — LU 2026-09-21, retrieved 2026-11-12
- Common mistake: "Missing return links: If page X links to page Y, page Y must link back to page X. If this is not the case for all pages that use `hreflang` annotations, those annotations may be ignored or not interpreted correctly." — [same page](https://developers.google.com/search/docs/specialty/international/localized-versions) — LU 2026-09-21, retrieved 2026-11-12

**HTML method**
- "For each variation of the page, include a set of `<link>` elements in the `<head>` element, one link for each page variant including itself. The set of links is identical for every version of the page." — [localized-versions](https://developers.google.com/search/docs/specialty/international/localized-versions) — LU 2026-09-21, retrieved 2026-11-12
- "The `<link>` tags must be inside a well-formed `<head>` section of the HTML. If in doubt, paste code from your rendered page into an HTML validator to ensure that the links are inside the `<head>` element. Additionally, don't combine `link` tags for alternate representations of the document; for example don't combine `hreflang` annotations with other attributes such as `media` in a single `<link>` tag." — [same page](https://developers.google.com/search/docs/specialty/international/localized-versions) — LU 2026-09-21, retrieved 2026-11-12

### Inferences
- If an hreflang target returns 4xx/5xx, Google ignores its content, so the return link cannot be confirmed and that pair drops out of the cluster. If the target is noindexed, it is not eligible for the cluster (office hours). If the target redirects, the redirect source is not indexed. In all three cases the alternate does not work. Point hreflang only at the final 200, indexable, self-canonical URL.
- An hreflang URL that canonicalises to another URL sends Google contradictory signals: hreflang marks the URL as a separate locale version, while the canonical marks it as a duplicate. Combined with the same-language canonical rule, the safe pattern is that every hreflang URL is its own canonical. Google's documentation does not state this as a rule. It is an inference from the cited text.

### Gaps
- No current Google documentation page says what happens when an hreflang target is non-200, redirected or canonicalised to a different URL. The January 2023 office-hours answer covers broken and `noindex` targets but not the "different canonical" part of the question.
- No 2025–2026 changelog entry explains the September 2026 edit to the localized-versions page beyond what the text comparison shows.

## 3. Multilingual sites: separate URLs, partially translated pages, auto-redirects, locale-adaptive pages

### Takeaway
Google wants a separate URL per language version, discoverable through links and annotated with hreflang. Googlebot mostly crawls from the USA, without `Accept-Language`, and does not vary location to find variants. Content swapped by IP, cookie or `Accept-Language` on one URL may therefore never be seen. Google says to avoid automatic language redirects and never adapt content by IP. Google determines the language from the visible main content. A page whose template is translated but whose main content (for example user or merchant text) stays in the original language is a duplicate of the original. Google still recommends hreflang for that case.

### Inferences
- **A translated page where user or merchant text stays in its original language:** if the main content is untranslated, Google treats the pages as duplicates and may cluster them. One URL becomes canonical and the others become alternates. Google still recommends hreflang for exactly this "template-only translation" case. Expect fewer independently indexed language URLs than languages offered. Translating the main content is what makes the pages distinct.
- **Auto-redirecting a root URL by `Accept-Language` or IP:** Googlebot sends no `Accept-Language` and mostly crawls from the US, so it would only ever see one variant. The documented pattern is a non-redirecting selector or default page marked `x-default`, with every language on its own crawlable URL.

### Gaps
- Google's pages give no threshold for how much of a page must be translated before Google stops treating it as a duplicate. "Primary content" and "main content" are not quantified.

## 4. Robots meta tag, X-Robots-Tag and robots.txt

### Takeaway
Supported page-level rules are `all`, `noindex`, `nofollow`, `none`, `nosnippet`, `indexifembedded`, `max-snippet`, `max-image-preview`, `max-video-preview`, `notranslate`, `noimageindex` and `unavailable_after`. `noarchive`, `nocache` and `nositelinkssearchbox` are unused. Rules are case-insensitive, the most restrictive rule wins, and robots meta is honoured even in `<body>` (documented 24 March 2026). In robots.txt only `user-agent`, `allow`, `disallow` and `sitemap` are supported. `crawl-delay` and any unlisted field, such as `host`, are ignored. The most specific (longest) matching path wins, and ties go to the least restrictive rule. A Disallow stops Google seeing an on-page `noindex`, so a blocked URL can still be indexed without content. Google calls the long-term outcome of "noindex, follow" "not defined" (office hours, 2024).

### Inferences
- `host:` lines (and `crawl-delay:`, `noindex:` and similar) in robots.txt have no effect on Google. A `crawl-delay` meant for Google should be replaced with the documented crawl-rate methods: 429/503 responses with `Retry-After`, or a special request (see section 6).
- For URLs that must leave the index, keep them crawlable and serve `noindex` (or 404/410). Add a robots.txt Disallow only after they have dropped out, if crawl load matters. A Disallow added first freezes the URL in the index without content.
- "noindex, follow" is not a reliable long-term way to pass discovery through a page. Detail pages need other stable, indexable link paths or sitemap inclusion.

### Gaps
- No current Google documentation page addresses "noindex, follow" over time. Only the April 2024 office-hours answer above does. An older (2017) office-hours video remark on the same topic is widely reported second-hand but was not verified here, so it is omitted.

## 5. Sitemaps

### Takeaway
A sitemap file may hold at most 50 MB uncompressed or 50,000 URLs, and an index file at most 50,000 `<loc>` entries. Files must be UTF-8 with absolute URLs. Google ignores `<priority>` and `<changefreq>`. It uses `<lastmod>` only when it is "consistently and verifiably" accurate and reflects a "significant" change. List only the canonical URLs you want in Search. Listing a different URL from the page's `rel="canonical"` sends conflicting signals. The image extension is still supported with only `<image:image>` and `<image:loc>`. Hreflang may go in sitemaps through `xhtml:link`. If a sitemap fetch fails, Google retries "for a few days" and then stops until you resubmit. Submission is "merely a hint".

### Inferences
- Non-canonical, redirecting, noindexed, robots-blocked or non-200 URLs do not belong in a sitemap. Google says to list the URLs you "want to see in Google's search results", which are the canonical URLs. Listing others sends conflicting canonical signals and inflates Search Console errors.
- An auto-generated `lastmod` that changes on every build, without a significant content change, is likely to fail Google's condition that `<lastmod>` be "consistently and verifiably […] accurate". Google may then ignore `lastmod` for the site.

### Gaps
- Google does not say how many "few days" a failed sitemap is retried, or whether Google follows an HTTP redirect on the sitemap URL itself. The "Redirects are not followed" sentence describes a report column.

## 6. HTTP status codes: soft 404s, not-found pages in JavaScript apps, 5xx/429, and 301/302/307/308

### Takeaway
Only 200 responses get indexed, and a 200 does not guarantee indexing. A "soft 404" is a 200 page that tells users the content doesn't exist, or that is empty. Google detects it from content, including the rendered result, and excludes it. Since 18 December 2025 Google also says non-200 pages may skip rendering. For JavaScript apps Google documents two options: a JavaScript redirect to a URL that returns a real 404, or injecting `noindex`. 4xx (except 429) removes URLs from the index. 5xx and 429 slow crawling, and URLs that stay in error get dropped. 301 and 308 are strong canonical signals and are equivalent. 302, 303 and 307 are weak.

### Cited Findings
**Status code handling (crawling docs; MOVED 18 Dec 2025)**
- "For Google Search, an HTTP `2xx (success)` status code doesn't guarantee indexing." `2xx`: "Google considers the content for processing (for example, in the case of Google Search, for indexing). If the content suggests an error for Google Search, an empty page or an error message, Search Console will show a `soft 404` error." — [How HTTP status codes affect Google's crawlers](https://developers.google.com/crawling/docs/troubleshooting/http-status-codes) — LU 2026-02-04, retrieved 2026-11-12
- `3xx`: "By default, Google's crawlers follow up to 10 redirect hops. However, specific products' crawlers may have different limits. For example, Googlebot generally follows 10 redirect hops when crawling for general web content, but Google Inspection Tools doesn't follow redirects. Any content Google receives from the redirecting URL is ignored, and the final target URL's content is processed instead." — [same page](https://developers.google.com/crawling/docs/troubleshooting/http-status-codes) — LU 2026-02-04, retrieved 2026-11-12
- `301`: "Google follows the redirect, and Google systems use the redirect as a strong signal that the redirect target should be processed." `302`: "By default, Google's crawlers follow the redirect, and Google systems use the redirect as a weak signal that the redirect target should be processed." `307`: "Equivalent to `302`." `308`: "Equivalent to `301`." **Soft 404 definition and detection**
- "A `soft 404` error is when a URL that returns a page telling the user that the page does not exist and also a `200 (success)` status code. ### Inferences
- In a server-rendered or hybrid app, the best not-found pattern is an HTTP 404 (or 410) on the original URL. Google gives the JavaScript redirect and injected `noindex` only as fallbacks for pure client-side routing. A 404 response's JavaScript may never run, so client-side logic cannot rescue a 404 page. The reverse also holds: a page that injects `noindex` starts as a 200 and depends on rendering succeeding.
- Serving 5xx or 429 for more than one or two days risks de-indexing. A redirect chain longer than 10 hops fails.

### Gaps
- Google publishes no quantitative threshold for soft-404 classification, for example how little content counts as "nearly blank".

## 7. JavaScript SEO: rendering, late or hidden content, tabs and accordions, links, pagination and infinite scroll, faceted navigation

### Takeaway
Googlebot crawls, queues every 200 page for rendering in an evergreen headless Chromium, and indexes the rendered HTML. Rendering is "not guaranteed", and Google canonicalizes and extracts some signals both before and after rendering. Since 3 February 2026 Googlebot reads only the first **2 MB** (uncompressed) of an HTML file; it was 15 MB. Content past that point is not indexed, however it is placed. Content that is in the DOM but visually collapsed (tabs, accordions, mobile menus) is acceptable and indexable. Content that loads only after a click, swipe or typing is never seen. Links must be `<a href>`. Use the History API, not fragments. Paginate with unique, crawlable `?page=n` URLs, each with its own canonical. Google no longer uses `rel=next/prev`. Faceted URLs should be blocked from crawling or kept tidy, and empty combinations should return 404.

### Inferences
- **Content late in the HTML:** anything beyond the first 2 MB of uncompressed HTML is cut off before indexing, wherever it sits in the document. Large inline JSON (for example serialized app state) placed before the main content can push that content past the cutoff.
- **Content inside an element with the `hidden` attribute, or moved into place by an inline script:** Google indexes the rendered HTML, flattens it, and explicitly accepts collapsed UI (tabs, accordions, burger menus). Text that is in the DOM is therefore available to Google whether it is visually hidden or relocated by script. Rendering is "not guaranteed" and some extraction happens before rendering. The safest pattern keeps the content in the server HTML in its final position. The snippet docs also make clear that collapsed content is less likely to earn "read more" deep links.
- "Load more" buttons and infinite scroll without `<a href>` links to `?page=n` URLs leave items beyond the first batch undiscoverable through that list.

### Gaps
- No Google documentation explicitly addresses the HTML `hidden` attribute, `display:none`, or content relocated by inline script. The guidance above is the nearest official text.
- Google does not publish rendering-queue latency figures beyond "a few seconds, but it can take longer than that".

## 8. Mobile-first indexing: content and structured-data parity

### Takeaway
Google indexes and ranks the mobile version, crawled with Googlebot Smartphone. With dynamic serving or separate mobile URLs, the mobile HTML must match desktop on primary content, headings, title and meta description, images and alt text, structured data, robots meta and robots.txt rules. Content present only on desktop is effectively invisible. Responsive sites satisfy parity by design.

### Inferences
- With responsive design, the parity checklist mainly applies to anything rendered differently by breakpoint-specific JavaScript. Examples are components that mount only above a desktop breakpoint, and structured data injected only in a desktop layout. Such content is absent from what Googlebot Smartphone indexes.

### Gaps

Its removal is not logged in either changelog. The current crawl-budget page (LU 2026-07-22) was "polished and clarified" on 22 July 2026.

## 9. Changes, deprecations and announcements in 2025–2026 (consolidated, in-scope only)

### Takeaway
2025–2026 brought no change to the core rules. The changes are relocations and precision edits: crawling docs moved (Nov–Dec 2025), noindex+JS and canonical+JS were clarified (Dec 2025), non-200 pages may skip rendering (Dec 2025), Googlebot's HTML cutoff is now 2 MB instead of 15 MB (Feb 2026), robots meta in `<body>` is honoured (documented Mar 2026), and new statements cover URL case-sensitivity, hreflang code case and regional-variant canonicalization (2026). Automated-translation robots.txt advice was removed (Jun 2025).

### Cited Findings
Unless marked otherwise, each item's source is the [Search Central documentation updates](https://developers.google.com/search/updates) page (LU 2026-11-09) or the [Google crawling documentation changelog](https://developers.google.com/crawling/docs/changelog) (LU 2026-10-30), both retrieved 2026-11-12. Items marked "(text comparison)" have no changelog entry and come from comparing archived and current versions of the Google page.
- **2025-03-05. CHANGED.** AI Mode was added to the robots meta tag documentation. `nosnippet` and `max-snippet` now explicitly cover AI Overviews and AI Mode inputs.
- **2025-06-11. REMOVED.** Guidance to use robots.txt to block automatically translated pages ("docs-only change, no change in behavior"). See section 3.
- **2025-06-18. CHANGED (docs only).** "Revamped the URL structure documentation". "This is a docs-only change, no change in behavior."
- **2025-08-28. NEW.** JavaScript-based paywall guidance.
- **2025-11-20. MOVED.** Crawling documentation moved to `developers.google.com/crawling`. "The content hasn't changed, only the location". The moved pages include the overview of Google crawlers and fetchers, verifying Google requests, reducing crawl rate, common crawlers, and the robots.txt specification.
- **2025-12-15. CHANGED.** noindex and JavaScript: old "skips rendering" became "may skip rendering"; the behaviour "is not well defined and might change". See section 7.
- **2025-12-17. NEW.** Canonical and JavaScript: keep the canonical identical in raw and rendered HTML, or omit it from the raw HTML. "Canonicalization happens before and after rendering". See section 1.
- **2025-12-18. NEW.** "If the HTTP status code is non-`200` […] rendering might be skipped." See sections 6 and 7.
- **2025-12-18. MOVED.** Faceted navigation, crawl budget, HTTP status codes and DNS/network error pages moved to the crawling site ("The functionality hasn't changed"). The 301/302 wording changed from "should be canonical" to "should be processed". The detailed soft-404 guidance now sits on "Troubleshoot Google Search crawling errors" (observed, not logged).
- **2026-02-03. CHANGED.** Googlebot for Search crawls the "first 2MB of a supported file type, and the first 64MB of a PDF file". It was "the first 15MB". 15 MB is now the default for Google crawlers generally.
- **2026-02-11. MOVED.** Google crawler IP ranges moved to `/crawling/ipranges`. The old location still works "for the time being".
- **2026-03-04. REMOVED.** Accessibility section of JavaScript SEO basics ("using JavaScript to load content is not "making it harder for Google Search"").
- **2026-03-24. NEW (documentation of existing behaviour).** Robots meta tags outside the HTML `<head>` are respected. "The behavior didn't change but was previously undocumented."
- **2026-04-20. NEW.** "Read more" deep-link best practices: content should be "immediately visible … (and not hidden behind an expandable section or tabbed interface". Don't remove hash fragments on load.
- **2026-06-15. CLARIFIED.** llms.txt: "these files aren't needed for Google Search (and won't negatively or positively impact your visibility or rankings)".
- **2026-06-17. CHANGED.** The site-move guide now covers the Change of Address tool "for all subdomain variants (including www and non-www) during domain migrations".
- **2026-07-10. CHANGED.** Canonicalization troubleshooting: Google "might hold pages in a duplicate cluster for up to two weeks" after fixes.
- **Between the 2026-07-10 and 2026-08-20 versions. NEW (text comparison).** Canonicalization page: for same-language regional variants, "use both canonicalization and `hreflang`".
- **2026-09-21. NEW (text comparison).** Localized-versions page: "The `hreflang` value is case-insensitive". The "es-419 … aren't supported" sentence was added earlier, between the LU 2024-11-28 and LU 2025-12-22 versions.
- **2026-10-06. CHANGED.** `Retry-After` header details were added to the crawl-rate reduction guide ("not new").
- **2026-10-21/23. CHANGED.** URL structure: hyphens vs underscores. The current page also states that Google's URL handling "is case sensitive (for example, Google treats both `/APPLE` and `/apple` as distinct URLs…)". That sentence is absent in the 2025-02-04 version; the exact date of addition is unknown.
- **2026-10-23. NEW.** robots.txt spec: rule paths are compared in percent-encoded form, and percent-encoding is recommended.
- **Context, 2024 (pre-window deprecations still in force):** `noarchive` retired (2024-10-02); unlisted robots.txt fields declared unsupported (2024-10-07); URL parameter best practice (2024-10-23); mobile link parity note (2024-11-01); `nositelinkssearchbox` retired (2024-11-29); cache-control support documented (2024-12-09); faceted navigation documentation (2024-12-17); robots.txt error handling consolidated (2024-12-18). Infinite-scroll guidance migrated to the docs (2024-09-17) "There is no change in the guidance".

### Inferences
- An auditor applying pre-December-2025 guidance should re-check three things. First, client-side canonical or noindex manipulation, which Google now explicitly discourages. Second, error pages returning non-200 while relying on JavaScript, since they may never be rendered. Third, very large HTML documents, where the cutoff is now 2 MB.

### Gaps
- Several page edits carry new footer dates but have no changelog entry. Examples are the canonicalization page (2026-08-20), localized-versions (2026-09-21) and the consolidate page's redirect wording. Their changes could only be identified by text comparison where an archived copy existed.
- Recent Search Central blog posts (feed titles retrieved 2026-11-12) included none on canonicalization, hreflang, robots or JavaScript rendering rules. The feed listing was not exhaustive for 2025.
